## Тимлид — архитектура, интеграция, демо

**Зона:** целостность решения, приоритеты, сквозной демо-сценарий, приёмка работ, `PROGRESS.md`.

**Задачи**
1. Пройти все 5 сценариев в приложении (`npm start` → http://localhost:8080) и утвердить демо-скрипт (ниже).
2. Еженедельно принимать работу по чек-листу «Definition of Done»: тесты зелёные, документ обновлён, скриншоты актуальны.
3. Отвечать за границы MVP: что входит в демо, а что заявляется только как дорожная карта.
4. Согласовать с продуктом и экономистами единую терминологию: М2/М5, КТГ, ММО, ПАРМ, ЕТО.

**Концепции, которые нужно уметь объяснить**
- Offline-first: локальная БД — источник истины для интерфейса.
- Ассистент — дополнительный контур к «Мобильному ТОРО», а не его замена.
- Человек в контуре: ИИ рекомендует, специалист решает, критичные случаи — только ответственное лицо.
- Объяснимость: каждая рекомендация трассируется до правил, замеров и случаев.

**Демо-скрипт (5–7 минут)**
1. Обзор парка → **S1**: однозначная причина, решение «устранить на ММО».
2. **S2**: несколько причин → проверки → «Демо: подставить замеры» → пересчёт → однозначно.
3. **S3**: «данных недостаточно» — агент не гадает, а называет конкретные замеры.
4. **S4**: красный экран; механик не может допустить машину (🔒), может только старший механик и только с комментарием.
5. Включить «Имитировать отсутствие связи» → принять решение → очередь 1 → выключить → синхронизация → М2 ушло.
6. Показать журнал и экран «Почему так решено».

## Влад — бэкенд (узел карьера, интеграции)

**Сделано в зоне (`server/server.js`, `server/server.test.js`):**
- Sync API: пакетный приём, идемпотентность по id, контроль sha256.
- Раздача базы правил с хешем и подписью (HMAC — демо).
- Журнал событий на сервере.
- Формирование сообщения вида М2 для SAP ТОРО (`sap-outbox.jsonl`).
- Авторизация устройства токеном, защита от выхода за каталог статики.

**Задачи**
1. Заменить JSON-хранилище на PostgreSQL (Postgres Pro): таблицы `sync_items`, `journal`, `rulebase_versions`, уникальный индекс по `id` — идемпотентность на уровне БД.
2. Спецификация адаптера SAP ТОРО: поля М2/М5, маппинг `causeGroup` → каталог повреждений/причин SAP, способ передачи (интеграционная шина / RFC / OData) — оформить как документ, код — заглушка.
3. Адаптер диспетчерской системы (Wenco): чтение последних параметров по машине → эндпоинт `/api/telemetry/:id`. В клиенте сейчас имитация `telemetryFor()`.
4. Подпись правил асимметричным ключом (прод: ГОСТ Р 34.10-2012). Клиент проверяет открытым ключом — сейчас клиент проверяет только sha256.
5. Эндпоинт метрик пилота по журналу: время «дефект → решение», доля согласий с агентом, доля запросов данных.

**Концепции:** идемпотентность, at-least-once delivery + дедупликация, контролируемая синхронизация, подписанные артефакты, edge-сервер в изолированной сети pLTE без выхода в интернет.

## Макс — фулстек (ядро, ML, перенос на Kotlin)

**Сделано в зоне (`core/`):**
- Диагностическое ядро: правила с состояниями FIRED/PENDING, поиск похожих случаев, softmax-ранжирование.
- Статусы CLEAR / MULTIPLE / INSUFFICIENT / CRITICAL, ранжирование проверок.
- Хук `mlRanker` для ML-модели, трассировка.
- Справочный модуль на BM25 (`core/knowledge.js`).

**Задачи**
1. Перенести ядро в Kotlin-модуль. Функции чистые, без I/O — перенос механический. Тесты `core/*.test.js` → JUnit с теми же кейсами (золотые тесты).
2. ML-модуль: когда появится выгрузка М2/М5 с причинами — обучить градиентный бустинг (признаки: симптомы, нормированные отклонения параметров, модель, наработка), экспорт в ONNX, подключение через `mlRanker`. Метрики: top-1/top-3 accuracy, калибровка.
3. Room + SQLCipher вместо IndexedDB, ключ в Android Keystore.
4. Эксперимент (не в MVP): локальная малая LLM (llama.cpp) поверх `knowledge.js` для ответов на вопросы своими словами. Ответ строго со ссылкой на документ, без генерации порогов.

**Концепции:** гибрид экспертной системы и CBR (case-based reasoning), объяснимый ИИ, «данных недостаточно» как полноценный ответ, ML только как дополнительный голос при наличии данных, версионирование моделей.

- `core/demo-data.js` — синтетический парк, история, 5 сценариев.

**Задачи**
1. Заменить **демонстрационные пороги** (`PROFILES`) на значения из руководств производителей. Каждому значению — источник. Пороги — главный риск достоверности.
2. Сверить перечень причин и проверок с типовыми неисправностями из материалов кейса; дописать правила для непокрытых симптомов (износ ходовой, стук в редукторах, отказ автосмазки…).
3. Расширить тестовые сценарии: по одному на каждую модель парка.
4. Заполнить перечень «что найти в кейсе» и таблицу AS-IS (`docs/process.md`, пп. 2 и 6).

**Как добавить правило** (`core/rules.js`):
```js
{ id: 'R-XXX-01', title: 'Понятное название',
  all: [{ sym: 'SYMPTOM_ID' }, { p: 'paramKey', op: '>', lim: 'paramKey.warn' }],
  causes: { CAUSE_ID: 1.0 },           // вес 0.2…1.5
  critical: 'Причина запрета (только для опасных состояний)' }
```
После правки запустить `npm test` — тест целостности поймёт опечатки в ID.

**Концепции:** пороги и зоны, сочетания признаков, «типовая неисправность», данные с указанием источника.
